# debt-health-check-blind-on-windows

Зона: приборы студии (`gamestudio/health-check.sh`) — вне `ZONES` проекта, игры не касается.
Размер: M. Роль: Developer.

## Что не так

`health-check.sh` на Windows **не падает, а врёт с уверенным видом** — тот самый класс отказа,
против которого он сам и написан («прибор, который льстит, бесполезен так же, как молчащий»).
Проверено прогоном 23.09.2026 на машине владельца:

| раздел | что печатает | правда |
|---|---|---|
| 1. Кто держит машину | `load average 1 мин:  на 1 ядрах` — пусто и единица | `uptime` и `sysctl -n hw.ncpu` — команды macOS, в Git Bash их нет |
| 1. Верхние пять по CPU | пустой список | `ps -eo pid,ppid,etime,pcpu,args` из Git Bash видит только процессы MSYS, а не Windows |
| 2. Осиротевшие долгожители | «осиротевших нет» | не проверено вовсе: перебирать нечего |
| 2а. Чья нагрузка | «из верхних десяти по CPU НАШИХ: **0 из 10**» плюс совет не сокращать волну | число выдумано: список пуст, `grep -c` по пустоте даёт ноль |
| 3. Брошенные браузеры | «брошенных съёмочных браузеров нет» | не проверено, причина та же |

**Цена уже заплачена в тот же день.** Producer проверял, не остались ли процессы от снятых деревьев
воркеров, сделал это тем же `ps` из Git Bash, получил пустоту и доложил владельцу «чужих процессов
не осталось». Через час выяснилось, что `ps` не видит и самого приложения: `dnd-master.exe` работал
с PID 25252, а прибор Producer'а его не показывал. То есть слепота прибора уже один раз стала
ложным утверждением владельцу.

## Что нужно

Разделы 1, 2, 2а и 3 обязаны работать на Windows и **остаться работающими на macOS**: папка
`gamestudio/` переносимая (см. `PORTING.md`), и «переписать под Windows» тут означает **развилку по
платформе**, а не замену одного частного случая другим.

Опора на Windows — PowerShell, потому что он единственный видит настоящую картину:

- ядра — `$env:NUMBER_OF_PROCESSORS`;
- мгновенная загрузка — `(Get-CimInstance Win32_Processor).LoadPercentage` (в процентах, а не
  `load average`: **это другая величина**, и подписать её надо честно, иначе порог «load/ядра ≥ 4»
  из `usage-snapshot.sh` окажется несравним);
- процессы с родителем, возрастом и строкой запуска — `Get-CimInstance Win32_Process`
  (`ProcessId`, `ParentProcessId`, `CommandLine`, `CreationDate`). Именно эта тройка нужна разделу 2:
  сирота = родителя нет + старше часа + жжёт CPU;
- время процессора — `Get-Process` (`CPU` в секундах). **Внимание:** это НЕ проценты. Признак
  «жжёт больше 20 %» на Windows придётся считать иначе — либо долей CPU-секунд к возрасту, либо
  двумя замерами с интервалом. Что выбрано — назвать словами и объяснить, почему.

Платформу определять по `uname` (`MINGW*`/`MSYS*` — Windows, `Darwin` — macOS, `Linux` — Linux), а
не по наличию команд: отсутствующая `uptime` уже один раз прошла молча.

**Там, где раздел на текущей платформе не поддерживается, он обязан сказать это вслух и не
печатать цифр.** Ноль, который значит «не проверено», хуже пустоты.

## Заодно, в том же файле — ствол не `main`

Разделы 5 и 8 сравнивают ветки с `main`, а ствол этого проекта — `dnd-app`. Отсюда сегодняшний
вывод «РАБОТА БЕЗ ИСПОЛНИТЕЛЯ: dnd-app — 587 коммитов ждут стадии», то есть прибор объявил
бесхозной работой весь проект. Имя ствола взять из профиля (`.studio/project.conf`, новая
переменная с умолчанием `main`), а не вшивать.

## Чего НЕ делать

- **Не заводить второй прибор.** Правится существующий файл; «health-check-win.sh» рядом — это два
  владельца одного факта.
- **Не ломать macOS-ветку.** Числа и пороги в ней добыты замерами 10-11 августа 2026 и остаются как
  есть.
- Не трогать `usage-snapshot.sh` и `work-check.sh`: они после коммита `087ee30` работают, и
  разрешение интерпретатора пробой (`PY`) уже сделано во всех трёх — повторять не надо.
- Не переписывать прибор на Python целиком. Соблазн понятный, но тогда правило «прибор запускается
  одной строкой из любой оболочки» перестаёт держаться, а питон уже один раз оказался заглушкой.

## DoD

- На Windows разделы 1, 2, 2а и 3 печатают настоящие числа: ядра, загрузку, имена и возраст верхних
  процессов, долю своих.
- Ни один раздел не печатает цифру там, где он ничего не проверил.
- Имя ствола читается из профиля проекта; на `dnd-app` раздел 8 больше не объявляет ствол
  бесхозной работой.
- macOS-ветка сохранена, и в отчёте сказано, чем это проверено (хотя бы разбором кода по веткам
  `uname`, если машины под рукой нет).
- Назван способ, которым на Windows считается «жжёт CPU», и почему он сопоставим с прежним порогом.

## Критерии приёмки

- Прогон прибора на этой машине печатает ядра не «1», а настоящее число, и в верхних процессах
  видно `dnd-master.exe`, когда приложение владельца запущено (проверяется прямо: поднять окно,
  прогнать прибор, увидеть строку).
- Строка «из верхних десяти по CPU НАШИХ» показывает ненулевое число, когда работает хотя бы один
  воркер или само приложение.
- Раздел 8 на чистом дереве молчит, а не перечисляет ствол.

## Критерии тестирования

- **Наблюдаемым поведением прибора, а не разбором кода:** запустить приложение владельца
  (`npm run tauri dev`), прогнать прибор, показать в отчёте строку, где `dnd-master.exe` назван по
  имени с возрастом. Это ровно тот случай, который прибор сегодня проспал.
- Отрицательная проверка: оставить висеть процесс-сироту (например, `node -e "setInterval(()=>{},1e9)"`,
  запущенный отвязанно) и убедиться, что раздел 2 его называет. Потом снять и убедиться, что раздел
  замолчал. Без этой пары раздел считается непроверенным.
- Назвать код выхода прибора в обоих случаях: с находками и без.
