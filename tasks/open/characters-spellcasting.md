# characters-spellcasting

Размер: L

Зависимости: `rules-spells-data` (нужны `Spell`/`get_spells`) должна быть смержена в ствол ДО начала
этой карточки — без готовой структуры заклинания выбирать в мастере персонажа нечего. Проверить
перед стартом: `git log main --oneline | grep rules-spells-data` (или эквивалент) — если пусто,
работа ещё не готова, не начинать.

## Контекст

`CharacterWizard.tsx` уже знает, у какого класса есть заклинания на 1 уровне
(`CLASS_SPELLCASTING_ABILITY` в `characterCreationData.ts`, шесть классов) и уже показывает шаг
«Итог» с текстом-заглушкой: «Списка заклинаний в приложении пока нет — заговоры и заклинания 1
уровня выбираешь сам по книге» (см. `spellAbility &&` блок, ~строка 1088). Эта заглушка убирается —
заменяется реальным выбором.

SRD 5.1 задаёт количество известных/подготовленных заговоров и заклинаний 1 уровня на 1 уровне
персонажа по классу в таблицах прогрессии классов (та же таблица, что даёт `spellAbility` —
`rules.json → classes-*`, раздел заклинательства каждого класса). Взять эти числа из уже
существующего `rules.json` (открыть нужные `classes-*` записи и найти в `blocks` таблицу/абзац про
заклинания 1 уровня) — не выдумывать и не гадать по памяти о D&D, у каждого класса свои числа и своя
механика (Волшебник и Бард знают фиксированный список, Жрец/Друид «подготавливают» из всего списка
класса каждый день — для этого приложения, где нет системы дней/отдыха, оба варианта реализовать как
один и тот же UX «выбери N заговоров и M заклинаний 1 уровня из списка своего класса на шаге
создания» — разница между «известные» и «подготавливаемые» это разница книжного текста, не разница
поведения приложения на этом этапе).

## Что нужно

1. **`Character` получает поля** (TS `types.ts` + Rust `model.rs`, тот же паттерн
   `#[serde(rename_all = "camelCase", default)]`, что уже применён для `gender`/`age`):
   - `knownCantrips: string[]` — id заговоров (`Spell.id`).
   - `knownSpells: string[]` — id заклинаний 1 уровня.
   - `spellSlotsLevel1Max: i32` / `spellSlotsLevel1Current: i32` — 0 у не-заклинателей.
   Персонажи без заклинательного класса получают пустые списки и нулевые ячейки — не показывать им
   ничего заклинательного нигде в интерфейсе.

2. **Шаг «Итог» мастера персонажа**: там, где сейчас текст-заглушка про заклинания — реальный выбор:
   загрузить `get_spells`, отфильтровать по `classes.includes(currentClassId)` и `level === 0` /
   `level === 1`, дать выбрать ровно нужное число заговоров и заклинаний 1 уровня (число — из
   `rules.json`, см. выше; хардкодить числа по классу в самом мастере можно, если это ровно те же
   числа, что в `rules.json` — не расходиться с уже показанным на шаге класса текстом). Кнопка
   «Создать персонажа» неактивна, пока заклинатель не выбрал ровно нужное число (как уже сделано для
   имени — `disabled={!name.trim()}`).

3. **`ImportPage.tsx`** (сохранение персонажа из импортированного текста) — как и для
   `gender`/`age`, проставить безопасный дефолт (пустые списки, нулевые ячейки) для импортированных
   персонажей, не оставлять поля неинициализированными.

4. **`CharactersPage.tsx` — карточка персонажа**: для заклинателей (непустой `knownCantrips` или
   `knownSpells`) — свёрнутый блок `<details>` «Заклинания», по образцу существующего блока
   «Инвентарь»: список известных заговоров/заклинаний (имя, можно кликом открыть полное описание —
   или просто показать по наведению/списком с уровнем, на усмотрение исполнителя), строка вида
   «Ячейки 1 уровня: 2/3» и кнопка «Восстановить все ячейки» (в приложении нет системы отдыха —
   ручное восстановление, тот же принцип, что уже применён к HP через `apply_damage` с отрицательной
   дельтой на вкладке «Кубики»: ресурс меняется вручную, когда в приложении нет автоматического
   триггера для этого).

## DoD

- Все шесть классов-заклинателей на шаге «Итог» показывают реальный список заклинаний своего класса
  вместо текста-заглушки; персонаж создаётся с корректно заполненными `knownCantrips`/`knownSpells`/
  `spellSlotsLevel1Max` (число ячеек 1 уровня на 1 уровне персонажа — тоже из `rules.json`, тот же
  раздел класса).
- Не-заклинатели (Боец, Плут, Варвар и т.д.) не видят вообще никакого UI про заклинания ни на шаге
  «Итог», ни в карточке персонажа.
- `$GATES_CMD` зелёный целиком, включая существующий Rust-тест на десериализацию старого JSON
  персонажа без новых полей (расширить тем же паттерном, что уже есть в `model.rs` для
  `background`/`gender`/`age`).

## Критерии приёмки

- Реальный сценарий: создать персонажа-Волшебника через мастер, выбрать заговоры и заклинания 1
  уровня из списка Волшебника (не Барда — списки разные) — готовый персонаж в `CharactersPage`
  показывает выбранные заклинания и полные ячейки 1 уровня. Потратить ячейку (следующая карточка
  батча это включит через бой, либо вручную если в этой карточке уже есть способ) — нажать
  «Восстановить все ячейки» — ячейки полные снова.
- Создать персонажа-Бойца — на шаге «Итог» нет вообще ничего про заклинания, в карточке персонажа
  тоже нет блока «Заклинания».

## Критерии тестирования

- Тест в `CharacterWizard.test.tsx`: для класса-заклинателя выбрать N заговоров и M заклинаний,
  создать персонажа — проверить `knownCantrips`/`knownSpells`/`spellSlotsLevel1Max` в объекте,
  переданном в `addCharacter`; кнопка «Создать» заблокирована, пока выбрано не ровно нужное число.
- Тест, что не-заклинатель проходит мастер без единого упоминания заклинаний в DOM шага «Итог».
- Тест дефолта из импорта (по аналогии с существующим тестом на `gender`/`age` в
  `ImportPage.test.tsx`).
