# ui-visual-and-sound-polish

Размер: L

Зона: `ui-shell`. Роль-исполнитель — `ui-developer` (см. `gamestudio/roles/ui-developer.md` и
`roles/_common.md`), не `developer`.

## Контекст

Владелец продукта, после `ui-typography-overhaul` (декоративный шрифт заголовков + выделение
терминов, уже смёржено), считает саму вёрстку и цвет всё ещё «унылыми и скучными», хочет звук на
нажатия кнопок и отдельно — графическое оформление броска кубиков (`DicePage.tsx`, сейчас чисто
текстовый лог без единого рисунка). Несколько независимых запросов в одной карточке, потому что все —
про общее ощущение от интерфейса и все идут одному исполнителю.

**Источник звука (клика и броска кубиков) решён заранее, не предлагать альтернатив**: короткие звуки
синтезируются программно (Web Audio API — `OscillatorNode`/`GainNode`/`AudioBufferSourceNode` с шумом
для «стука» костей, короткая огибающая), без внешних аудиофайлов и без обращения к интернету — та же
причина, что и у политики «никаких чужих ассетов» для картинок бестиария
(`SRD-only-content-boundary`), только для звука. Тембр — на усмотрение исполнителя, в стиле игры
(фэнтези), не игровой «бип» по умолчанию.

## Что нужно

### Фаза 1 — делать сразу, без этапа предложений (тут нечего согласовывать)

#### 1. Звук на нажатие кнопки

- Один короткий синтезированный звук на клик **любой** кнопки в приложении.
- Технически: **один** источник звука и **один** способ его повесить на все кнопки — не размножать
  `onClick`-обработчики по каждому месту, где сейчас стоит `<button>` (их в проекте уже десятки).
  Правильный паттерн — один обработчик на уровне `document`/`#root` (capture-фаза), реагирующий на
  клик по `button`/`[role="button"]`, либо эквивалент с тем же результатом (один явный владелец
  факта «кнопка нажата — играть звук», не переписывать саму кнопку). Выбор способа — на исполнителе,
  но в отчёте назвать, где именно живёт этот единственный обработчик.
- `disabled`-кнопка звук не издаёт (клик по ней не проходит).
- Простой способ выключить/убавить звук не нужен — это не просили, не добавлять лишнего UI ради
  контроля громкости.

#### 2. Звук броска кубиков

- На каждый вызов `roll()` в `DicePage.tsx` (успешный результат, не при ошибке выражения) — свой
  короткий синтезированный звук «броска» (шумовая огибающая, не тот же тон, что у клика кнопки —
  это разные события и должны различаться на слух).
- «Записать вручную» (`recordManual`) — это не бросок кубика в приложении, а фиксация внешнего
  результата: звук броска здесь не нужен (обычный звук клика по кнопке «Записать вручную», из п.1,
  остаётся).

### Фаза 2 — сначала предложить, вёрстку/иконки делать только после согласия

#### 3. Предложения по внешнему виду

Владелец назвал явно: цветовая схема, иконки, выпадающие меню (`<select>`/списки выбора) и списки
предлагаемых предметов (`datalist`/подсказки в полях вроде «Новый предмет») шрифтом более
тематическим (заголовочный декоративный шрифт из `ui-typography-overhaul` уже есть — расширить его
применение туда, где сейчас обычный текст).

- Подготовить **2–3 разных варианта** визуального направления (не один) — цветовая палитра + пример
  иконок + пример оформления выпадающего меню/списка предметов. Каждый вариант — отдельные файлы
  (макеты/палитры/примеры иконок) в `docs/art/inbox/`, с понятными именами (`variant-a-...`,
  `variant-b-...`).
- В отчёте — краткое описание каждого варианта (2-3 предложения) и ссылка на файлы. **Не начинать
  переверстку интерфейса, пока владелец продукта не выбрал вариант** — это отдельный шаг, не в этой
  сессии дальше предложения, если явного согласия не поступило.
- Если согласие получено в ходе этой же сессии (Producer передаст ответ владельца) — реализовать
  выбранный вариант по всему приложению (все экраны: мастер, карточка персонажа, правила, бой,
  дневник, бестиарий), тем же принципом «пройтись везде», что уже был в `ui-typography-overhaul` —
  не оставлять часть экранов в старом виде.
- Бестиарий (`src-tauri/bestiary/images/`) не трогать ни в каком из вариантов — по-прежнему ручная
  работа владельца, см. `roles/ui-developer.md → Запрещено`.

#### 4. Графическое оформление костей (`DicePage.tsx`)

Сейчас результат броска — только число в тексте (`item.result.rolls`), без единой иконки. Каждая
кость из `QUICK_DICE` (d4/d6/d8/d10/d12/d20/d100) визуально должна соответствовать своей форме
(число граней узнаётся по рисунку, не только по подписи «d20» рядом) — это тоже иконки, часть той же
Фазы 2, тем же визуальным языком, что выбран в п.3, не отдельный несвязанный стиль.

- В варианты п.3 включить хотя бы один пример кости (например, d20) — чтобы стиль костей утверждался
  вместе с общим направлением, а не отдельным решением потом.
- После согласия — нарисовать (SVG, не растровый файл — масштабируется без потери резкости) все 7
  граней `QUICK_DICE`. d100 может переиспользовать рисунок d10 с пометкой «×10», это стандартная
  практика для настольных кубиков — не рисовать несуществующую отдельную форму.
- В логе бросков (`dice-page__log`) каждая запись показывает иконку кости, соответствующей
  выражению, а не только текст; при составном броске (например `2d6+3`, несколько значений в
  `item.result.rolls`) — иконка кости с итоговым числом на грани, отдельные кубики по каждому
  значению из `rolls` рисовать не нужно (это визуальная кость-иконка «какая кость бросалась», не
  честная анимация физического броска).

## DoD

- Клик по любой активной кнопке приложения издаёт синтезированный звук; один обработчик, не
  размноженные `onClick`.
- Успешный бросок на «Кубиках» издаёт свой синтезированный звук, отличимый от звука клика кнопки.
- В `docs/art/inbox/` лежат 2-3 предложенных визуальных варианта (включая пример кости) с кратким
  описанием каждого в отчёте.
- Если получено согласие на вариант — он реализован по всем экранам (включая иконки всех 7 костей
  `QUICK_DICE` в логе бросков), `$GATES_CMD` зелёный.
- Если согласия не было — карточка не закрывается переверстовкой/иконками костей, только звуками;
  вариант оформления остаётся открытым вопросом для следующей сессии (описать в отчёте, что именно
  ждёт решения).

## Критерии приёмки

- Открыть любой экран, понажимать несколько разных кнопок (в т.ч. `disabled`) — звук на активных,
  тишина на `disabled`.
- Бросить кубик на «Кубиках» — звук броска, отличный от звука клика по кнопке «Бросить».
- В `docs/art/inbox/` — 2-3 узнаваемо разных по цвету/иконкам/акцентам варианта, не вариации одного и
  того же.
- (Если вариант выбран и реализован) Бросить d4, d6 и d20 — три разных по форме иконки в логе, не
  одна и та же картинка с разной подписью.

## Критерии тестирования

- Тест на источник звука клика (юнит-уровня, если тестируемо без реального `AudioContext` в jsdom —
  замокать/проверить, что фабрика звука вызывается на клик кнопки и не вызывается на клик по
  `disabled` или не-кнопке); если `AudioContext` недоступен в среде тестов — не морочиться, годно
  честно указать в отчёте, что синтез проверен вручную (сборкой) и почему юнит-проверке не поддаётся.
- Тест, что `roll()` вызывает звук броска ровно при успешном результате (не при ошибке разбора
  выражения).
- (Если вариант выбран и реализован) Тест, что лог бросков рендерит иконку кости, соответствующую
  разобранному выражению (`d20` → иконка двадцатигранника и т.п.), не одну общую иконку на все.
