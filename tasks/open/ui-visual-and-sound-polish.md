# ui-visual-and-sound-polish

Размер: L

Зона: `ui-shell`. Роль-исполнитель — `ui-developer` (см. `gamestudio/roles/ui-developer.md` и
`roles/_common.md`), не `developer`.

## Контекст

Владелец продукта, после `ui-typography-overhaul` (декоративный шрифт заголовков + выделение
терминов, уже смёржено), считает саму вёрстку и цвет всё ещё «унылыми и скучными» и хочет звук на
нажатия кнопок. Два независимых запроса в одной карточке, потому что оба — про общее ощущение от
интерфейса и оба идут одному исполнителю.

**Источник звука клика решён заранее, не предлагать альтернатив**: короткий «клик» синтезируется
программно (Web Audio API — `OscillatorNode`/`GainNode`, короткая огибающая), без внешнего аудиофайла
и без обращения к интернету — та же причина, что и у политики «никаких чужих ассетов» для картинок
бестиария (`SRD-only-content-boundary`), только для звука. Тембр — на усмотрение исполнителя, в стиле
игры (фэнтези), не игровой «бип» по умолчанию.

## Что нужно

### 1. Звук на нажатие кнопки (делать сразу, без этапа предложений — тут нечего согласовывать)

- Один короткий синтезированный звук на клик **любой** кнопки в приложении.
- Технически: **один** источник звука и **один** способ его повесить на все кнопки — не размножать
  `onClick`-обработчики по каждому месту, где сейчас стоит `<button>` (их в проекте уже десятки).
  Правильный паттерн — один обработчик на уровне `document`/`#root` (capture-фаза), реагирующий на
  клик по `button`/`[role="button"]`, либо эквивалент с тем же результатом (один явный владелец
  факта «кнопка нажата — играть звук», не переписывать саму кнопку). Выбор способа — на исполнителе,
  но в отчёте назвать, где именно живёт этот единственный обработчик.
- `disabled`-кнопка звук не издаёт (клик по ней не проходит).
- Простой способ выключить/убавить звук не нужен — это не просили, не добавлять лишнего UI ради
  контроля громкости.

### 2. Предложения по внешнему виду (сначала предложить, вёрстку делать только после согласия)

Владелец назвал явно: цветовая схема, иконки, выпадающие меню (`<select>`/списки выбора) и списки
предлагаемых предметов (`datalist`/подсказки в полях вроде «Новый предмет») шрифтом более
тематическим (заголовочный декоративный шрифт из `ui-typography-overhaul` уже есть — расширить его
применение туда, где сейчас обычный текст).

- Подготовить **2–3 разных варианта** визуального направления (не один) — цветовая палитра + пример
  иконок + пример оформления выпадающего меню/списка предметов. Каждый вариант — отдельные файлы
  (макеты/палитры/примеры иконок) в `docs/art/inbox/`, с понятными именами (`variant-a-...`,
  `variant-b-...`).
- В отчёте — краткое описание каждого варианта (2-3 предложения) и ссылка на файлы. **Не начинать
  переверстку интерфейса, пока владелец продукта не выбрал вариант** — это отдельный шаг, не в этой
  сессии дальше предложения, если явного согласия не поступило.
- Если согласие получено в ходе этой же сессии (Producer передаст ответ владельца) — реализовать
  выбранный вариант по всему приложению (все экраны: мастер, карточка персонажа, правила, бой,
  дневник, бестиарий), тем же принципом «пройтись везде», что уже был в `ui-typography-overhaul` —
  не оставлять часть экранов в старом виде.
- Бестиарий (`src-tauri/bestiary/images/`) не трогать ни в каком из вариантов — по-прежнему ручная
  работа владельца, см. `roles/ui-developer.md → Запрещено`.

## DoD

- Клик по любой активной кнопке приложения издаёт синтезированный звук; один обработчик, не
  размноженные `onClick`.
- В `docs/art/inbox/` лежат 2-3 предложенных визуальных варианта с кратким описанием каждого в
  отчёте.
- Если получено согласие на вариант — он реализован по всем экранам, `$GATES_CMD` зелёный.
- Если согласия не было — карточка не закрывается переверстовкой, только звуком; вариант оформления
  остаётся открытым вопросом для следующей сессии (описать в отчёте, что именно ждёт решения).

## Критерии приёмки

- Открыть любой экран, понажимать несколько разных кнопок (в т.ч. `disabled`) — звук на активных,
  тишина на `disabled`.
- В `docs/art/inbox/` — 2-3 узнаваемо разных по цвету/иконкам/акцентам варианта, не вариации одного и
  того же.

## Критерии тестирования

- Тест на источник звука (юнит-уровня, если тестируемо без реального `AudioContext` в jsdom —
  замокать/проверить, что фабрика звука вызывается на клик кнопки и не вызывается на клик по
  `disabled` или не-кнопке); если `AudioContext` недоступен в среде тестов — не морочиться, годно
  честно указать в отчёте, что синтез проверен вручную (сборкой) и почему юнит-проверке не поддаётся.
