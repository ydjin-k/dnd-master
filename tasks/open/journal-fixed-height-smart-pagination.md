# journal-fixed-height-smart-pagination

Размер: M. Зона: `journal`. Роль-исполнитель — `ui-developer` (см. `gamestudio/roles/ui-developer.md`
и `roles/_common.md`).

## Контекст

После `journal-pagination-and-layout-cleanup` владелец продукта нашёл новую проблему: если записать
длинный текст (или несколько записей, суммарно занимающих много места) на разворот, сам гримуар
физически растягивается по высоте — `src/ui/pages/JournalPage.css`, `.journal-page` сейчас
`min-height: 520px` (не фиксированная высота), а `.journal-page__list` —
`grid-template-rows: repeat(3, max-content)`, то есть строки грида подстраиваются под контент и
тянут за собой всю обложку/корешок/рамку.

**Владелец продукта выбрал направление** (обсуждали варианты): гримуар должен оставаться **визуально
статичным** (фиксированная высота, никогда не тянется), а раскладка **умно упаковывает** записи по
развороту — не всегда ровно 3+3: например, 6 коротких записей на развороте, ИЛИ 2 средних на
странице, ИЛИ 1 большая на всю страницу — сколько влезает по примерному объёму текста, а остальное
уходит на следующий разворот через уже существующую пагинацию (`journal-pagination-and-layout-cleanup`,
`spreadIndex`/`turnPage` в `JournalPage.tsx`).

**Важное ограничение с прошлой карточки**: `jsdom` (окружение тестов) не считает реальную раскладку
(уже сталкивались с этим на баге селектора кубиков) — поэтому точный алгоритм должен работать на
**примерном бюджете объёма текста** (например, по длине строки `entry.text`, не по измерению
фактической отрендеренной высоты через `ref`/`ResizeObserver`) — это делает логику упаковки чистой
функцией, которую можно нормально протестировать в vitest, без реальной раскладки DOM.

## Что нужно

1. Сделать `.journal-page` (и, если нужно, `.journal-page__list`) **действительно фиксированной
   высоты** (`height`, не `min-height`) — подобрать значение, при котором большая часть обычных
   записей помещается без дополнительных мер; `overflow: hidden` там уже есть.
2. Написать чистую функцию упаковки (например, в `JournalPage.tsx` или отдельном модуле рядом) —
   вход: отсортированный массив записей (уже есть, новые сверху) + константа «бюджет» (число, по
   ощущению — сколько символов текста примерно помещается в одну колонку страницы при текущих
   `clamp(1.35rem, 2vw, 1.65rem)`/`line-height: 1.28`; можно завести по одной константе на левую/
   правую колонку, они одинаковые). Логика: жадно добавлять записи в текущую колонку, пока
   суммарная длина текста (+ небольшая фиксированная добавка за «шапку» записи — дату и отступы) не
   превысит бюджет; при превышении — новая запись уходит в следующую колонку (правая страница того
   же разворота, затем левая страница следующего разворота, и так далее). Функция возвращает массив
   «разворотов», каждый — `{ left: Entry[]; right: Entry[] }`.
3. **Одна запись длиннее бюджета целой колонки** — не разбивать её на части (запись — атомарна),
   поместить её одну в колонку; как аварийный предохранитель именно для этого редкого случая — у
   `.journal-entry__text` можно завести `max-height` с `overflow-y: auto` **только на уровне текста
   одной записи** (не всей страницы/книги), чтобы даже экстремально длинная запись не тянула рамку
   гримуара — прокручивается только её собственный текст, разворот остаётся на месте.
4. Подключить функцию упаковки вместо текущего плоского `entries.slice(spreadIndex * 6, ...)` —
   `spreadCount`/пагинация (кнопки «вперёд»/«назад», звук `page-flip.mp3`, сброс на первый разворот
   при добавлении записи) уже реализованы в прошлой карточке, их не трогать, только источник данных
   для текущего разворота меняется с фиксированного среза на результат упаковки.
5. Подобрать значение бюджета опытным путём в живом Tauri-приложении (визуально: короткие записи —
   действительно помещается около 3 на колонку при типичной длине сообщения; книга не растягивается
   ни на коротких, ни на длинных записях).

## DoD

- Разворот книги (`.journal-page`) никогда не меняет высоту от объёма текста записей — фиксированная
  высота при любом содержимом.
- Записи распределяются по колонкам/разворотам по объёму, а не жёстко по 3+3: короткие — несколько на
  колонку, длинные — меньше или по одной.
- Экстремально длинная одиночная запись не растягивает книгу — прокручивается только её собственный
  текст.
- Существующая пагинация (кнопки, звук, сброс на первую страницу при добавлении) продолжает работать
  на новой упаковке.
- `$GATES_CMD` зелёный.

## Критерии приёмки

- Записать несколько очень коротких записей на разворот — видно больше, чем 3 на странице, если
  влезает по объёму (не жёстко ограничено тремя).
- Записать одну очень длинную запись — гримуар не растягивается, текст записи скроллится внутри
  своего блока.
- Записать средних размеров записи, суммарно превышающие бюджет одной страницы, — лишние уходят на
  следующий разворот, доступный через уже существующее перелистывание.

## Критерии тестирования

- Юнит-тест на саму функцию упаковки (чистая логика, без рендера DOM): короткие записи — несколько
  на колонку; одна запись длиннее бюджета — одна в колонке; общее число записей на выходе равно
  входному (ничего не теряется и не дублируется).
- Существующие тесты `JournalPage.test.tsx` (пагинация, сброс страницы, добавление/удаление) остаются
  зелёными с поправкой на новый источник данных для видимых записей, если тесты полагались на жёсткий
  срез по 6.
