# ui-layout-systemic-audit-and-fixes

Размер: XL (аудит и правки по всему приложению — не влезет в одну сессию воркера целиком, см. «Как
поступить, если не успеваешь» ниже). Зона: `ui-shell` — внешний вид и раскладка, все страницы и
общие компоненты. Роль-исполнитель — `ui-developer` (`gamestudio/roles/ui-developer.md`).

## Контекст

Владелец продукта прислал скриншоты (не дошли до Producer текстом — воркеру нужно будет
воспроизвести живьём в Tauri-окне, скриншоты не приложены к этой карточке) и текстом описал
повторяющиеся по всему приложению дефекты вёрстки: слишком тесное расположение текста, неудачное
распределение по колонкам, неодинаковые внутренние отступы, большие пустые области, возможное
горизонтальное переполнение/обрезание содержимого.

**Один конкретный случай Producer нашёл и подтвердил в коде** (не предположение — это тот самый
компонент, о котором пишет владелец: «общий компонент «переключатель + подпись»»):

`src/ui/pages/CharactersPage.tsx` — один и тот же CSS-класс `.character-card__asi-mode`
(`CharactersPage.css` строка 175, `display: flex` без `flex-direction`/`flex-wrap` — то есть строка
без переноса) используется для **трёх структурно разных** списков переключателей:
1. `asiMode` (строка ~891) — 2 коротких взаимоисключающих варианта, радио корректны семантически.
2. Выбор архетипа при левел-апе (строка ~821) — до нескольких вариантов, у каждого `<strong>Имя</strong> —
   длинное описание`, тоже радио (единственный выбор), но текст многострочный.
3. `pendingChoice` (строка ~851) — выбор архетипной особенности (`SubclassChoice`), где вариантов
   может быть **много** (например, у Барда «Коллегия знаний» — 3 из 18 навыков, запись 76 в
   `tasks/DONE.md`) и тип инпута **уже правильно** переключается `pick === 1 ? "radio" : "checkbox"`
   (строка 855) — так что чекбоксы для множественного выбора в коде уже есть, дефект чисто визуальный:
   у 18 длинных вариантов в одну `flex`-строку без переноса контейнер неизбежно ужимает каждый
   вариант до узкой колонки, вызывая перенос текста по одному слову на строку — отсюда и «узкие
   вытянутые тёмные прямоугольники», и смещение кружка/чекбокса относительно многострочной подписи
   (у `<label><input/>текст</label>` без `display:flex; align-items` инпут по умолчанию не
   центрируется по высоте многострочного текста).

**Вторая часть той же находки** — цвет и форма переключателей. `theme.css` строка 154-156 задаёт
`accent-color` только для `input[type="checkbox"]` — у `input[type="radio"]` (7 мест в
`CharacterWizard.tsx`/`CharactersPage.tsx`, найдены через grep) нет ни одного правила темизации,
поэтому они рендерятся нативным видом браузера/WebView2 (белый кружок, ярко-синий выбранный) —
отсюда и «визуально отличаются от остального интерфейса».

Это не значит, что вся карточка сводится к этим двум находкам — они лишь доказывают, что
систематическая причина существует в общих стилях, как и предполагает владелец. Остальное требует
живого визуального прохода по всем экранам, как просит владелец ниже.

## Что нужно

Владелец прямо расписал порядок работы — следовать ему, а не изобретать свой:

1. **Пройти все экраны, вкладки и диалоги** приложения (Приключение, Бой, Кубики, Персонажи —
   карточка персонажа и мастер создания, Дневник, Правила, Бестиарий, лаунчер/циферблат кампаний),
   включая состояния с длинными названиями/описаниями и разным количеством элементов (например,
   персонаж с 18-вариантным выбором навыков, длинным списком инвентаря, длинными именами
   рас/подклассов). **Уточнение владельца**: не нужно живьём проверять каждый класс/подкласс по
   отдельности — достаточно взять любую расу и класс Волшебник (у него есть длинные варианты выбора
   архетипа/заклинаний, этого достаточно, чтобы вскрыть системную причину) и проверить на нём;
   находка причины и её исправление в общем компоненте/стиле логически должны сработать для всех
   остальных классов/подклассов без отдельной проверки каждого.
2. **Найти причины повторяющихся дефектов в общих стилях/компонентах** — начать с `theme.css` (общие
   правила тем, кнопок, инпутов) и с находки про `.character-card__asi-mode`/`accent-color`
   радио/чекбоксов выше, но не ограничиваться ими. Проверить: ограничения ширины (`max-width`),
   настройки колонок (`grid-template-columns`/`flex` без `flex-wrap`), перенос текста (`white-space`,
   отсутствующий `word-wrap`/`overflow-wrap`), отступы, и как глобальные правила влияют на списки
   переменной длины.
3. **Сначала общие компоненты и стили, потом точечные проблемы экранов** — чинить в этом порядке, не
   наоборот, чтобы не патчить одно и то же дважды.
4. **Число колонок — по доступному месту**: текстовые блоки должны оставаться читаемой ширины,
   корректно переноситься, занимать нужную высоту (не фиксированную, если контент длиннее).
5. **Единые отступы**: внутри карточек, между заголовками/описаниями/списками — по согласованным
   правилам (не обязательно вводить новую систему токенов, если существующих переменных темы
   достаточно — на решение воркера).
6. **Чекбоксы/радио отдельно, по находке выше**: там, где переключатель семантически позволяет
   выбрать несколько вариантов одновременно (`pendingChoice` с `pick > 1`) — квадратный чекбокс,
   там где ровно один вариант (`asiMode`, `pendingChoice` с `pick === 1`, метод характеристик в
   визарде, выбор архетипа) — круглая радиокнопка, но **обе темизированные** (не нативный вид),
   выровненные с первой строкой подписи, без узких «прямоугольников» вокруг. Разделить общий
   компонент «переключатель + подпись» так, чтобы контейнер с многими длинными вариантами не ужимал
   их в узкие колонки (вертикальный список, а не `flex`-строка без переноса, либо `flex-wrap` с
   разумной минимальной шириной варианта).

7. **Кнопка «Создать персонажа по правилам» (`CharactersPage.tsx` строка ~1510-1517)** — владелец
   отдельно попросил: сейчас она рендерится после всего `<ul className="characters-page__list">`,
   то есть в самом низу страницы, ниже всех карточек персонажей — «теряется внизу». Перенести в
   верхнюю часть страницы, в один ряд с `<h2>Персонажи</h2>` (строка 1486), в правый верхний угол;
   саму кнопку сделать компактнее (меньше текущего размера). Открытие мастера (`panel === "wizard"`)
   и его расположение под кнопкой не менять — только позицию/размер самой кнопки.

**Сохранить без изменений**: текущую цветовую гамму (переменные темы), шрифты, весь текст/контент и
функциональность (клики/состояния/данные не менять, только раскладку и стили) — кроме позиции/
размера кнопки «Создать персонажа по правилам» из пункта 7, которая прямо об этом просит.

**Почему запрет на палитру и шрифты остаётся в силе, хотя владелец уже утвердил новый стиль.**
10 сентября 2026 владелец прислал макет системы стиля «Астральный атлас» и решил привести к нему
всё приложение — но это **отдельная карточка `ui-astral-atlas-style-system`**, которая идёт
**после** этой, а не вместо неё. Здесь по-прежнему чинится раскладка, и палитра/шрифты не
трогаются. Причина разделения: обе карточки правят одни и те же файлы, а при смешении невозможно
отличить регрессию от перекраски от регрессии от правки раскладки. Красить сломанную раскладку
раньше, чем она починена, — закрашивать трещины. Если по ходу работы захочется поправить цвет или
шрифт «заодно» — не делать, а назвать в отчёте: это заберёт соседняя карточка.

## Как поступить, если не успеваешь за одну сессию

Полный визуальный проход по всем экранам при разных размерах окна — большой объём. Первым делом
починить общий механизм (пункты 2-3, 6 выше — это System-level причина, от которой зависит всё
остальное), затем пройтись по как можно большему числу экранов вживую. В отчёте явно перечислить,
какие экраны проверены и починены, какие остались — для карточки-продолжения.

## DoD

- Текст и элементы не перекрывают друг друга ни на одном проверенном экране.
- Содержимое не обрезается, остаётся доступным (в диалогах/карточках нет невидимых частей).
- На поддерживаемых размерах окна нет непредусмотренной горизонтальной прокрутки.
- Длинные тексты/названия корректно переносятся, не вываливаются и не ужимаются в узкие колонки.
- Однотипные компоненты (карточки, переключатели, списки) имеют согласованные отступы.
- Радио- и чекбоксы темизированы одинаково (не нативный вид), тип инпута соответствует семантике
  (один/много вариантов), выровнены с первой строкой подписи.
- Цветовая гамма, шрифты, контент и функциональность не изменились.
- `$GATES_CMD` зелёный.

## Критерии приёмки

- Пройти все вкладки и ключевые диалоги (левел-ап с длинным списком вариантов выбора, мастер
  создания персонажа, бестиарий, дневник с длинными записями) при разных размерах окна — нет
  наложений, обрезаний, горизонтального скролла.
- Открыть панель выбора архетипной особенности с большим числом вариантов (например, Бард
  «Коллегия знаний», 3 из 18) — варианты читаемы, не сжаты в узкие колонки, чекбоксы/радио выглядят
  единообразно с остальным интерфейсом.
- Приложить скриншоты «было/стало» хотя бы для 2-3 самых показательных случаев (в т.ч. панель
  выбора с длинным списком) в финальном отчёте.

## Критерии тестирования

- Если тесты на конкретные CSS-классы/структуру существуют (`CharactersPage.test.tsx`,
  `CharacterWizard.test.tsx` и т.п.) и правки меняют структуру DOM (например, тип инпута
  чекбокс/радио) — обновить их вместе с правкой, не оставлять красными.
- Визуальные правки (раскладка/отступы/перенос) не обязаны иметь отдельную юнит-пробу — это не
  повод не проверять их вживую (см. критерии приёмки), но и не повод плодить пробы, которые не
  сторожат конкретный дефект (см. `gamestudio/roles/_common.md`, «проба заводится только на
  критический сценарий или на найденный баг»).
