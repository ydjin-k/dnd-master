# bug-campaign-atomic-write

Размер: M

## Что не так

Каждая Tauri-команда, меняющая кампанию (`submit_custom_action`, `ask_oracle`,
`adjust_chaos_factor`, `choose_option`, `start_adventure` в `src-tauri/src/lib.rs`), делает так:

```rust
let mut state = active(&app)?;      // storage::load_active — берёт и отпускает STORAGE_LOCK
// ...мутирует state в памяти...
storage::save_campaign(&app, &state)?;  // берёт и отпускает STORAGE_LOCK заново
```

Между чтением и записью замок не удерживается. Если два таких вызова наложатся друг на друга
(например, игрок быстро кликает дважды, или два независимых действия идут почти одновременно),
оба читают один и тот же снимок кампании, оба мутируют свою копию независимо, и тот, кто
сохраняется вторым, молча затирает изменения первого.

Найдено внешним ревью (Codex), проверено вручную по коду `storage.rs`/`lib.rs` — гонка
подтверждается логикой, тот же класс проблемы уже один раз ловился в проекте (см. тест
`concurrent_first_launch_migrates_legacy_exactly_once` — там гонку на миграции уже закрыли одним
замком на всю операцию; здесь то же самое нужно для обычных команд чтение-правка-запись).

## DoD

- Одна операция "прочитать активную кампанию → применить правку → сохранить" выполняется под ОДНИМ
  удержанием `STORAGE_LOCK` от начала до конца, а не двумя отдельными.
- Механизм выбирает исполнитель: например, добавить в `storage.rs` функцию вида
  `with_active_locked(app, |state| -> Result<(), String> { ...мутация... Ok(()) })`, которая сама
  делает load+mutate+save под одним `STORAGE_LOCK.lock()`, и переписать перечисленные команды в
  `lib.rs` на неё. Не обязательно называть именно так — важен результат: замок не отпускается между
  чтением и записью одной и той же логической операции.
- Затронуть только эти команды и `storage.rs` — не трогать бой (`combat.rs`/`start_combat` и
  соседние), у него отдельный путь и в ревью Codex к нему претензий не было.

## Критерии приёмки

- Реальный сценарий: два потока (как в существующем тесте на гонку миграции) параллельно выполняют
  разные мутации над одной и той же кампанией (например, оба добавляют разную запись в
  `adventureLog`) — после обоих сохранений на диске должны остаться ОБЕ мутации, а не только одна.

## Критерии тестирования

- Новый тест в `src-tauri/src/storage.rs` (или там, где будет жить новая функция), по образцу
  `concurrent_first_launch_migrates_legacy_exactly_once`: два потока читают-мутируют-пишут кампанию
  параллельно через новый атомарный путь, после `join()` обе мутации видны в сохранённом состоянии.
- Отрицательная проба: прогнать этот тест на СТАРОМ коде (два отдельных lock-а) — должен падать
  (терять одну из мутаций хотя бы иногда; если гонка не детерминирована с первого раза — крутить
  в цикле в тесте, как уже сделано для миграции). Убедиться в падении, потом вернуть починку.
- `$GATES_CMD` (`npm run gate`) зелёный целиком.
