# characters-class-feature-progression-1-5

Размер: XL (12 классов × 5 уровней прогрессии способностей — большая карточка, скорее всего не
влезет в одну сессию воркера целиком, см. «Как поступить, если не успеваешь» ниже).

## Контекст

Владелец продукта заметил, что при левел-апе персонажа (`CharactersPage.tsx: applyLevelUp`) растут
только `level`, `maxHp`/`currentHp` и (на нужных уровнях) `subclass` — но **не** классовые
способности, растущие с уровнем: у заклинателей не появляются новые ячейки заклинаний и новые
заклинания выше 1 круга, а у остальных классов не появляются/не растут собственные фичи (Ярость
варвара, кости Скрытой атаки плута, очки Ки монаха, Каналирование божественности жреца/паладина,
Дуэльный стиль/Бросок кубика Стойкости бойца и т.д. — по всем 12 базовым классам).

**Важная находка (сильно ускоряет задачу, не игнорировать и не изобретать заново):** `rules.json`
(`src-tauri/rules/rules.json`) **уже содержит полные официальные таблицы прогрессии всех 12 базовых
классов SRD 5.1**, переведённые на русский — вплоть до 20 уровня, хотя приложению нужны пока только
уровни 1–5. Подтверждено построчным поиском: таблица Барда с ячейками по кругам и заговорам/
заклинаниями (`rules.json:4387` и далее), полный текст Вдохновения барда с прогрессией кости
(к6→к8→к10→к12) на строках `4817-4833`, таблица Варвара с Яростью (`5088`+) и т.д. — по остальным
классам аналогичные таблицы и текстовые блоки способностей уже есть в файле. **Значит для этой
карточки НЕ нужен PHB и не нужно ничего заново переводить с английского** — вся прогрессия уже
переведена и лежит в `rules.json`, нужно её вычленить в структурированные данные и подключить к
левел-апу. (Хозяин проекта попросил использовать PHB для вдохновения барда специально — но текст
Вдохновения барда с полной прогрессией по уровням **уже есть в `rules.json` из официального SRD
5.1**, так что PHB для этого пункта не понадобился; см. `srd-only-content-boundary` — контент
приложения принципиально не берётся из личной копии PHB, даже точечно.)

**Ограничение по потолку уровня (подтверждено владельцем):** прогрессию делать строго в рамках
текущего `MAX_LEVEL = 5` (`CharactersPage.tsx`). Подъём самого потолка уровня — другая задача, в
этой карточке не трогать.

## Что нужно

1. **Извлечь данные из `rules.json` в структурированный формат**, а не парсить текстовые таблицы на
   лету — по каждому из 12 классов, для уровней 1–5:
   - Ячейки заклинаний по кругам (только для заклинателей — Бард/Жрец/Друид/Чародей/Волшебник —
     полные ячейки; Колдун — своя таблица Pact Magic, она в SRD отдельная и меньше по числу ячеек;
     Паладин/Следопыт — half-caster таблицы, тоже отдельные в SRD).
   - Известные заговоры / известные или подготавливаемые заклинания по уровню (обе механики важны:
     Бард/Чародей/Колдун/Следопыт — «известные», фиксированный список; Жрец/Друид/Волшебник/Паладин
     — «подготавливаемые», доступен весь список класса нужного круга, игрок выбирает подмножество
     каждый день — см. пункт 3 про UI).
   - Прочие классовые фичи по уровню — как минимум: Ярость варвара (число использований + бонус
     урона по уровню), Скрытая атака плута (кости), Боевой стиль/доп. фичи бойца, Ки-очки монаха,
     Каналирование божественности жреца/паладина (число использований), Дикий облик друида,
     Экспертиза барда/плута, Бонусные заклинания следопыта и т.п. — текст беру из уже переведённых
     блоков `rules.json`, не сочинять.
   - Разумный формат — новый файл вроде `src-tauri/rules/class_progression.json` (тот же паттерн
     `include_str!`/загрузчика, что у `rules::load_rules`/`spells::load_spells`), с массивом записей
     `{classId, level, feature: {name, description}}` плюс отдельные структурированные поля для ячеек
     заклинаний/известных заклинаний по уровню (не текстом, а числами — левел-ап должен уметь читать
     их программно).
2. **Модель персонажа**: расширить `Character` (`model.rs` + зеркальный TS-тип в `state/types.ts`) —
   сейчас есть только `spell_slots_level1_max/current`. Нужны поля под ячейки 2–5 круга (только для
   классов, у кого они по таблице бывают на уровнях ≤5), плюс что-то отслеживающее использования
   классовых фич с ограниченным числом раз (Ярость/Каналирование/Ки и т.п. — можно один общий
   механизм вида `Vec<{featureId, usesMax, usesCurrent}>`, переиспользуемый для всех классов, вместо
   отдельного поля на каждую фичу).
3. **Левел-ап** (`applyLevelUp` в `CharactersPage.tsx`): на каждом уровне подтягивать из новой таблицы
   прогрессии и применять — новые ячейки заклинаний (пересчитать max, current не трогать так же, как
   уже не трогает HP-прирост существующий currentHp), новые заговоры/фичи с ограниченным числом
   использований (обновить max, current — по стандартному SRD-правилу восстанавливаются на длинном
   отдыхе, уже кнопка "восстановить ячейки" есть для заклинаний — `restoreSpellSlots`, обобщить и на
   новые фичи). Для классов с **известными** заклинаниями, где список растёт (Бард/Чародей/Колдун/
   Следопыт) — при левел-апе, если открылась новая ячейка заклинания, дать игроку выбрать одно новое
   заклинание своего класса нужного круга (простой список/дропдаун, тот же паттерн, что уже
   используется для выбора подкласса на левел-апе — `subclassPanelOpen`/`confirmSubclass`). Для
   классов с **подготавливаемыми** заклинаниями (Жрец/Друид/Волшебник/Паладин) новых заклинаний в
   `known_spells` при левел-апе не добавлять — им и так открыт весь список класса нужного круга при
   подготовке (если у приложения ещё нет отдельного UI «подготовки» — заводить его не в этой
   карточке, просто не блокировать левел-ап отсутствием этого UI).
4. **Видимость на левел-апе и карточке персонажа** (см. правило `dnd-master-review-step-rule` — оно
   про визард, но тот же принцип применим): при левел-апе выбор/факт получения новой фичи должен быть
   виден игроку (как уже видно получение подкласса), а на самой карточке персонажа — список активных
   классовых фич с их описанием и текущим числом использований (там же, где уже показаны заклинания/
   ячейки — `CharactersPage.tsx`), а не только сухие числа без объяснения, что это.

## Как поступить, если не успеваешь за одну сессию

12 классов × 5 уровней прогрессии — большой объём переноса данных. Коммитить инкрементально: сначала
инфраструктура (схема данных, формат `class_progression.json`, подключение к левел-апу) и заклинательные
классы (Бард/Жрец/Друид/Чародей/Волшебник/Колдун — уже есть база из карточки про заклинания), затем
не-заклинательные фичи остальных классов (Варвар/Боец/Монах/Паладин/Плут/Следопыт). В конце отчёта явно
указать, какие классы полностью прогрессируют 1→5, какие остались — для карточки-продолжения.

## DoD

- Левел-ап каждого из 12 классов на уровнях 1–5 даёт именно то, что предписывает официальная SRD
  таблица (ячейки заклинаний, известные/доступные заклинания, классовые фичи с числом использований).
- Данные взяты из уже переведённого `rules.json`, не выдуманы и не скопированы из PHB.
- Новая фича/ячейка видна игроку в момент левел-апа и постоянно — на карточке персонажа.
- Существующие тесты левел-апа/ASI/подкласса (`CharactersPage.test.tsx`) остаются зелёными без
  регрессий; `$GATES_CMD` зелёный.

## Критерии приёмки

- Создать заклинателя (например Барда), довести до 2 уровня — видно новую ячейку 1 круга (или круга,
  положенного по таблице) плюс новый заговор/заклинание согласно официальной прогрессии; довести
  Барда до 3 или 5 уровня, где меняется кость Вдохновения барда (к6→к8) — видно на карточке.
- Создать Варвара, довести до 2 уровня — видно новое число использований Ярости по таблице.
- Ни один класс не получает ячейки/фичи выше уровня 5 по таблице (потолок приложения).

## Критерии тестирования

- Юнит/интеграционный тест на левел-ап хотя бы одного full-caster (ячейки растут по таблице) и одного
  не-заклинателя (число использований фичи растёт по таблице), плюс класса с pact magic (Колдун) —
  отдельная таблица ячеек.
