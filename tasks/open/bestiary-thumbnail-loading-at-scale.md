# bestiary-thumbnail-loading-at-scale

Размер: M/L. Зона: `engine` (Rust) + `bestiary` (фронтенд), файлы `src-tauri/src/combat.rs`,
`src-tauri/src/lib.rs`, `src-tauri/src/storage.rs` (только переиспользовать `app_data_dir`, не
трогать), `src/ui/pages/BestiaryPage.tsx`. Роль-исполнитель — `developer`.

**Карточка-продолжение `bestiary-image-loading-hang` (запись 82 в `tasks/DONE.md`) — тот фикс не
полный, см. находку ниже.**

## Контекст

Предыдущая карточка уменьшила байты картинки (183 МБ → ~0.66 МБ на открытие вкладки), но **не
ограничила параллелизм самого пересчёта** — `BestiaryPage.tsx` всё ещё запускает 50 одновременных
`invoke("get_bestiary_image", ...)` при монтировании, каждый из которых синхронно ресайзит картинку
в Rust.

**Владелец продукта воспроизвёл зависание живьём после мержа этого фикса** — Producer подтвердил
это не со слов, а замером в реальном времени: опрос `Get-Process -Id <pid>` (Windows API
"отвечает/не отвечает", то же самое, что показывает диалог «Не отвечает») каждые 50-80мс поймал
главный процесс `dnd-master.exe` в состоянии `Responding=False` **на протяжении десятков секунд**
(наблюдался прирост CPU-времени процесса больше 90 секунд суммарно за эпизод), при этом дочерние
процессы WebView2 (рендер/GPU) в это время оставались в покое — то есть тяжёлая работа реально идёт
в Rust-части приложения, не в отрисовке страницы браузером.

Вероятная причина (нужно подтвердить замером в самой карточке, не гадать): 50 одновременных
Tauri-команд, каждая делает CPU-тяжёлый ресайз+перекодирование картинки — в **debug**-сборке
(`cargo run`, не release) `image`-крейт без оптимизаций может быть на порядок медленнее, чем
1.1с/50 картинок, замеренные воркером прошлой карточки в release-сборке. 50 таких задач разом на
машине с ограниченным числом ядер (замерено на 12 логических) может надолго забирать все ядра под
фоновый пул и не давать основному потоку/циклу сообщений вовремя прокачаться — отсюда «Не отвечает»
на десятки секунд, которое само проходит, когда пул освобождается.

**Владелец также прямо предупредил**: бестиарий в будущем вырастет до **200-300 тварей** — решение
обязано планироваться с этим запасом, не только чинить сегодняшние 50. Firing 200-300 одновременных
`invoke` при открытии вкладки было бы кратно хуже, чем сегодняшние 50.

## Что нужно

1. **Замерить и подтвердить причину в самой debug-сборке** (не полагаться на release-цифры прошлой
   карточки) — сколько реально стоит ресайз одной картинки и всех текущих 50 при параллельном
   запуске, и убедиться, что это объясняет наблюдаемые десятки секунд простоя. Число, не догадка.
2. **Кэшировать сгенерированные превью на диск** — сгенерированная уменьшенная JPEG-версия картинки
   не должна пересчитываться на каждое открытие вкладки. Писать кэш не рядом с забандленными
   оригиналами (в собранном приложении `resource_dir` может быть не доступен на запись), а в
   каталог данных приложения — тот же `app_data_dir(app)` (см. `storage.rs`, уже используется для
   файлов кампаний), например подкаталог `bestiary-thumbnails/`. Кэш ключуется по id твари + желаемый
   размер (список/деталь — два разных кэшируемых файла на тварь). Инвалидация не нужна — картинки
   бестиария статичны и бандлятся с приложением, не меняются в рантайме.
3. **Ограничить параллелизм самого пересчёта**, а не только доверять кэшу (первое открытие после
   установки/обновления всё равно пересчитывает всё с нуля) — например, семафор/счётчик, общий на
   все вызовы `get_bestiary_image` (через `tauri::State`, разумный размер — несколько единиц, не все
   доступные ядра целиком), чтобы даже 300 одновременных запросов от фронтенда физически ресайзили
   не более N картинок параллельно, а не все сразу.
4. **Спланировать явно на 200-300 тварей** — если картинки списка (сейчас все 50 запрашиваются сразу
   при монтировании) при таком масштабе всё ещё будут пытаться загрузиться все одновременно —
   рассмотреть ленивую загрузку по видимости в списке (например, `IntersectionObserver` на строку
   списка, или обычная пагинация/виртуализация списка), чтобы при открытии вкладки с 300 тварями не
   пытаться получить 300 превью одновременно, а только те, что реально видны на экране + небольшой
   запас. Выбор конкретного механизма — на решение воркера, главное — не проверять решение только на
   сегодняшних 50, если оно опирается на общее количество.
5. **Стресс-проверка на масштаб будущего**: временно (для проверки, не для коммита в данные)
   продублировать существующие 50 картинок под синтетическими id до ~300 и прогнать тот же сценарий
   открытия вкладки — подтвердить числом (замер CPU/времени, не «стало быстрее на глаз»), что при
   300 тварях зависания нет. Тестовые данные для этого шага не коммитить в `bestiary.json`/`images/`
   — это одноразовая проверка, а не наполнение бестиария (наполнение — отдельная карточка
   `bestiary-full-database-and-tab`, продолжение).

## DoD

- Повторное открытие вкладки «Бестиарий» (после первого прогрева кэша) не пересчитывает превью с
  нуля — использует кэш.
- Параллелизм ресайза ограничен явно (число, не «как получится»), не растёт линейно с числом тварей.
- Стресс-проверка на ~300 тварей (временных, не закоммиченных) подтверждает отсутствие зависания —
  числом.
- `$GATES_CMD` зелёный.

## Критерии приёмки

- В живом Tauri-окне (debug-сборка, как у владельца) открыть вкладку «Бестиарий» несколько раз
  подряд — зависания/статуса «Не отвечает» нет ни при первом (холодном), ни при повторных открытиях.
  Проверять через `Get-Process`/аналог отзывчивости, а не только «на глаз» — синтетический клик через
  accessibility API в этой карточке уже показал себя недостаточным для воспроизведения (см. отчёт
  Producer'а в истории сессии) — нужен замер поверх настоящего окна.
- Стресс-тест на ~300 тварей проходит без зависания, с named числами до/после.

## Критерии тестирования

- Тест, что повторный запрос одной и той же картинки/размера не запускает ресайз повторно (кэш
  реально используется — например, счётчик вызовов `image::open`/резайза через mock/spy).
- Тест, что параллелизм ресайза действительно ограничен (например, счётчик одновременно активных
  ресайзов не превышает заданный предел при N одновременных вызовов).
- Существующие тесты `bestiary-image-loading-hang` (размер превью на порядки меньше оригинала,
  сохранение пропорций) не сломать, обновить при необходимости под новую структуру кода.
