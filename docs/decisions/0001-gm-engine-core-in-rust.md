## 1. Решение

**Ядро GM Engine — модуль Rust `src-tauri/src/gm/`, рядом с `model.rs` и `storage.rs`.** В
TypeScript не остаётся ни одного решения движка: фронт показывает состояние и отправляет намерение.

Состав модулей (имена нужны, чтобы по ADR можно было писать карточки):

| модуль | что в нём | раздел ТЗ |
|---|---|---|
| `gm/state.rs` | `EngineState` — тип состояния движка; **поля приватны** | §3.3, §4.1 |
| `gm/mutate.rs` | `Mutation`, `Transaction`, `validate`, `apply` — единственный путь записи | §34, §37 |
| `gm/history.rs` | `Transaction` в `EngineState.history`, откат | §35 |
| `gm/rng.rs` | `seed`, `rng_state`, `next_u64`, `roll` | §22 |
| `gm/router.rs` | чистая функция `route(action) -> Module` | §5 |
| `gm/adapter.rs` | Rules Adapter: проверка навыка, спасбросок, бросок по сиду | §3.1 |
| `gm/oracle.rs` | вероятность, бросок, четыре исхода | §6 |
| `gm/facts.rs` | Fact Store | §4.6, §6.3 |
| `gm/scene.rs` | создание, завершение, переход сцены, напряжение | §7, §10 |
| `gm/world.rs` | локации, вход/выход | §4.4, §32 |
| `gm/actors.rs` | акторы, состояния | §4.3 |
| `gm/threats.rs` | угрозы, шкала осведомлённости | §4.5, §25 |
| `gm/events.rs` | Event Intent, Context Filter, выбор шаблона, fallback | §8, §9, §20, §21, §28 |
| `gm/explore.rs` | бюджет находок локации | §11 |

Состояние движка — **поле существующего документа кампании**, а не второй файл:

```rust
// model.rs
pub struct CampaignState {
    pub id: String,
    pub campaign_name: String,
    pub characters: Vec<Character>,
    pub journal: Vec<JournalEntry>,
    pub combat: Option<CombatState>,
    pub engine: Option<EngineState>,   // #[serde(default)] — старые сохранения читаются как None
}
```

Второй файл отвергнут: два документа расходятся при первой же правке — тот самый довод, которым
правка 16.09 запретила копировать статы бестиария в Actor (§4.3). Один файл даёт заодно и §6.3:
«не бросать Оракул, если факт уже есть» проверяемо только когда факт и бросок в одной транзакции.

### В какой форме ядро зовётся из интерфейса

Одна Tauri-команда на тип действия §5.1. Тело каждой — **один** вызов
`storage::with_active_locked` (`storage.rs:274`): чтение с диска, мутация, запись — под одним
удержанием `STORAGE_LOCK`, без окна между чтением и записью.

```rust
#[tauri::command]
fn gm_ask_oracle(app: AppHandle, question_key: String, probability: u8, modifier: i8)
    -> Result<GmResponse, String>;

pub struct GmResponse {
    pub state: CampaignState,   // для показа
    pub result: ResultObject,   // §33: исход, броски, изменения, продолжения, trace
}
```

Фронт принимает ответ существующим `runServerAction` (`src/state/CampaignContext.tsx:204`):
`commit(response.state)` — и ничего не вычисляет. **Ни `persist`, ни `persistWith` к состоянию
движка не прикасаются.** Команда получает намерение (действие, цель, вероятность, модификатор), а
не состояние: фронту нечем передать устаревший снимок, потому что он снимка не передаёт вовсе.

Первая пачка команд: `gm_create_scene`, `gm_end_scene`, `gm_ask_oracle`. Дальше — `gm_skill_check`,
`gm_explore`, `gm_trigger_event`, `gm_enter_location`.

### Что остаётся в TypeScript, и это не остаток, а владение

1. **Модификатор проверки** — `abilityMod`, `proficiencyBonusForLevel`, `SKILL_ABILITY`
   (`src/ui/characterCreationData.ts:30, 1045, 75`). Лист персонажа уже показывает эти числа
   (`CharactersPage.tsx:1334`); они уезжают в `gm_skill_check` **аргументом**. Движок их не
   пересчитывает и своей копии не держит.
2. **Текст.** Движок возвращает `summary_key`/`text_key` (§33), строку подставляет
   `src/ui/gm/eventText.ts`. Шаблонизатора с `{actor}` (§18.1) в v0.1 нет — три уровня текста
   §18.2 делаются тремя ключами.
3. **Показ.** Экран сцены читает `state.engine.*` и своего `useState` на эти данные не заводит.

Аргумент — не копия: значение живёт один вызов, записывается в `Transaction` ради объяснимости
(§23) и нигде не становится вторым авторитетным экземпляром. Именно этим он отличается от
`Combatant`, который копирует `max_hp`/`current_hp` персонажа (`combat.rs:517-531`) и потому
расходится с листом.

### Содержание событий

Машинная часть шаблонов (§9: `id`, `conditions`, `effects`, `text_key`, `weight`) — новый
`src-tauri/gm-content/events.json`, загрузчик по готовому образцу `rules.rs`/`spells.rs`
(`#[cfg(debug_assertions)]` → `CARGO_MANIFEST_DIR`, иначе `resource_dir`). Единое дерево
`/content` из §19 не заводится: содержание у нас разрезано по происхождению, а не по жанру —
SRD 5.1 в `src-tauri/rules/*.json`, переданное владельцем в TS
(`src/ui/eventTables/types.ts` объясняет, почему именно так). Слить их — сделать границу «всё из
rules.json — это SRD» непроверяемой.

**26 таблиц к100 в `src/ui/eventTables/` остаются на месте и с шаблонами §9 не сливаются.** Это
разные вещи: там описательная строка, которую игрок читает и применяет за столом, здесь — строка с
машинным `effects`, которую применяет движок. Одна таблица в двух видах — два владельца.

## 2. Цена отвергнутого

### Чем платим за Rust

- **Движок не может сам придумать проверку, которую никто не попросил**: модификатор приходит
  аргументом. Для v0.1 этого хватает — §41 требует только *интерфейс* Rules Adapter, а §30 ASSISTED
  GM и так предполагает подтверждение мастером. AUTO GM (§43, v0.3) потребует переноса трёх функций
  из `characterCreationData.ts` в Rust — это отдельная дорогая карточка, и она названа здесь, чтобы
  не оказаться неожиданностью.
- **Парная правка на каждый новый вид события**: ключ в `events.json`, строка в
  `src/ui/gm/eventText.ts`. Строк мало, но забыть половину легко — сторожит проба «на каждый
  `text_key` движка есть строка».
- **Круг через `invoke` на каждое действие**, показ обновляется после ответа. Латентность я не
  замерял и числа не называю; наблюдаемое основание — боевой экран уже работает именно так,
  кругом на каждый ход, и владельцем принят.
- Четвёртый файл содержания рядом с `rules.json`/`spells.json`/`bestiary.json`.

### Чем платили бы за TypeScript

- **Владельцем каждого факта движка стал бы фронт, а записать состояние с фронта можно только
  целым документом** через `save_campaign` (`lib.rs:45`, `CampaignContext.tsx:77`). Сцена,
  напряжение, факты и транзакции попали бы ровно на тот путь, где 136 уже случилась.
  `persistWith` + `latest` — заплатка в одном провайдере, а не свойство данных: идиома
  `{...current, facts: [...]}` по построению не может запретить писать `facts` кому-то ещё. В Rust
  приватность полей `EngineState` делает правило «писать только через `mutate::apply`»
  **проверяемым компилятором**, а не ревью. Это главный довод, и он не про язык, а про то, что
  запрет второго владельца здесь исполним машинно.
- **§22 и §44 шаг 11**: воспроизводимость потребовала бы ГСЧ в TS — то есть ВТОРОГО генератора
  рядом с `dice.rs`. Либо каждый бросок движка — отдельный круг в Rust за числом, и тогда
  детерминизм зависит от порядка асинхронных ответов.
- **§34/§35**: журнал транзакций жил бы в памяти вкладки и умирал при перезагрузке окна — либо
  уезжал на диск тем же целым документом.
- **§17**: движок, решающий «начинается ли бой», оказался бы по другую сторону границы от 2062
  строк `combat.rs`, которые бой ведут.
- **Что TS при этом выигрывает:** проверка навыка и заклинательные формулы под рукой, трёх
  переносов (модификатор, УС, текст) не нужно вовсе. Это единственная статья в его пользу, и она
  самая мелкая из перечисленных.

## 3. Владелец каждого факта

Читать так: **хранит** — где лежит единственный экземпляр; **меняет** — единственная функция,
которой это позволено; **показывает** — кто читает, не копируя.

| факт | хранит | меняет | показывает |
|---|---|---|---|
| сцена | `EngineState.scene: Option<SceneState>` | `gm/scene.rs`: `create_scene`, `end_scene`, `transition` | экран сцены из `state.engine.scene` |
| **напряжение** | `SceneState.tension` — **у сцены, не у кампании** | `gm/scene.rs::end_scene` (§7.2: −1/0/+1), `gm/events.rs::apply_effects` | экран сцены |
| цель сцены, теги, участники | `SceneState` | `gm/scene.rs` | экран сцены |
| **факты мира** | `EngineState.facts: Vec<Fact>` — **поле состояния, отдельного хранилища нет** | `gm/facts.rs`: `create_fact`, `update_fact` | панель «Активно» |
| акторы | `EngineState.actors: Vec<Actor>` | `gm/actors.rs`: `create_actor`, `update_actor` | экран сцены |
| статы актора | **не хранятся**: `Actor.rules_ref` → `bestiary.json` или `Character.id` | владелец статов — бестиарий / лист | `BestiaryPage`, `CharactersPage` по ссылке |
| HP актора | **нигде, и заводить нельзя** — в бою `CombatState.combatants`, вне боя `Character.current_hp` | `combat.rs` / лист персонажа | там же (см. расхождение 11) |
| локации | `EngineState.locations: Vec<Location>` | `gm/world.rs`: `create_location`, `enter_location`, `leave_location` | экран сцены |
| бюджет находок | `Location.discovery_slots` | `gm/explore.rs::explore` | экран сцены |
| угрозы | `EngineState.threats: Vec<Threat>` | `gm/threats.rs` | панель «Активно» |
| **осведомлённость** | `Threat.awareness` (§25) — **не в `Actor.states`** | `gm/threats.rs`, эффекты шаблонов | панель «Активно» |
| сюжетные линии | `EngineState.plot_threads` — **в v0.1 поля нет** (§41 не включает, §42 включает) | `gm/threads.rs`, с v0.2 | — |
| **seed** | `EngineState.seed: u64` | `gm/rng.rs::new_campaign_seed` — один раз при создании кампании, дальше не меняет никто | отладочный экран |
| **состояние ГСЧ** | `EngineState.rng_state: u64` — **владелец движок; сохранение только перевозит его** | только `gm/rng.rs::next_u64` | отладочный экран |
| **журнал транзакций** | `EngineState.history: Vec<Transaction>` | только `gm/mutate.rs::apply` | **никому** (§29.2) |
| **дневник кампании** | `CampaignState.journal` — владелец не меняется | `addJournalEntry` (`CampaignContext.tsx:159`) вместе с правилом набора страницы (`journalEntryText.ts`) | `JournalPage` |
| ход | `EngineState.turn: u32` | `gm/mutate.rs::apply`, +1 на транзакцию действия | отладочный экран |
| трассировка решения (§38) | **не хранится** — поле `ResultObject.trace` одного ответа | каждый модуль дописывает там, где решает | отладочный экран |
| модификатор проверки | `characterCreationData.ts`: `abilityMod`, `proficiencyBonusForLevel`, `SKILL_ABILITY` | там же | лист персонажа (уже) |
| УС проверки | `rules.json` → `gameplay-abilities`, таблица «Сложность Задачи» (5/10/15/20/25/30) | ничто, это SRD | UI предлагает выбор мастеру |
| текст события | `src/ui/gm/eventText.ts` по ключу | там же | экран сцены |

Два следствия, которые стоит прочитать вслух:

**Движок не пишет дневник сам.** Он возвращает `summary_key`, экран предлагает «В дневник», пишет
игрок — ровно как уже сделано у генератора событий (`AdventuresPage.tsx`: «Записывает только по
нажатию… Автоматически не пишется ничего»). Причина не в осторожности: правило набора страницы
дневника — дописывать в самую свежую, пока есть место — живёт в TS и принадлежит данным
(`journalEntryText.ts`). Движок, пишущий дневник из Rust, стал бы вторым владельцем этого правила.

**Трассировка рождается там, где принято решение.** Ни один экран не восстанавливает причину по
исходу. На пилоте экран ДОГАДЫВАЛСЯ о причине отказа маршруту и 29 мирных объектов из 51 называл
«сюда пути нет» — то есть врал игроку. `trace` заполняет тот, кто решает, и больше никто.

### §41 MVP v0.1 — по пунктам, чтобы ни один не остался без владельца

| § | пункт | хранит | меняет |

## 4. Чем это решение опровергается

Любого одного признака достаточно — он означает, что разрез по языку выбран не там.

1. **В дифе `gm/adapter.rs` появилась вторая копия формулы, которая уже есть в TS** —
   `abilityMod`, `proficiencyBonusForLevel`, `spellSaveDc`. Значит граница «модификатор приходит
   аргументом» не держит, и ядро надо было ставить в TS рядом с формулами. Проверяется гревом по
   дифу пачки, а не мнением.
2. **На экране сцены завёлся `useState`, повторяющий любое поле `state.engine.*`.** Значит круга
   через `invoke` не хватает для отзывчивости, и ради показа у факта появился второй владелец —
   то есть куплена ровно та поломка, от которой всё это строилось.
3. **§44 шаг 11 не сходится, пока бой не переведён на ГСЧ кампании.** Тогда «единый управляемый
   ГСЧ» (§22) и «бой остаётся на `thread_rng`» несовместимы, ядро и бой обязаны быть одним ГСЧ, и
   выбранный разрез неверен.

Признак 3 проверяется первой же пачкой; 1 и 2 — при приёмке каждой.

## 5. Rules Adapter: что делает и чего не делает

Утверждение карточки — «тонкая обёртка, реально добавляет ровно одно: проверку навыка» —
**подтверждено по существу и неверно в числе. Добавляет три вещи, и одну из них делегировать
нельзя вовсе.**

### Что действительно уже написано (проверено чтением)

| нужно движку | чем закрыто | проверено |
|---|---|---|
| разбор `2d6+3`, бросок | `dice.rs`: `roll_expression:146`, `parse:29` | есть |
| характеристики 4к6 | `dice.rs::roll_ability_scores:119` | есть |
| модификатор характеристики | `characterCreationData.ts::abilityMod:30` | есть |
| навыки и привязка к характеристике | `characterCreationData.ts`: `ALL_SKILLS:48`, `SKILL_ABILITY:75` | есть |
| владения | `Character.skill_proficiencies`, `saving_throw_proficiencies` (`model.rs:125-126`) | есть |
| бонус мастерства | `characterCreationData.ts::proficiencyBonusForLevel:1045` | есть |
| СЛ спасброска от заклинания | `characterCreationData.ts::spellSaveDc:4363` | есть |
| **УС проверки** | `rules.json` → `gameplay-abilities`, таблица «Сложность Задачи» | **есть, в карточке не названо** |
| бой | `combat.rs`: `start_combat:488`, `attack:683`, `apply_damage:689`, `cast_spell:720`, `end_turn:824`, `monster_auto_turn:850` | есть |
| справочники | `rules.rs::load_rules`, `spells.rs::load_spells`, `combat.rs::load_bestiary:198` | есть |
| листы персонажей | `characters.rs::load_character_presets`, `CharactersPage.tsx` | есть |

### Чего нет — три вещи, не одна

1. **Проверка навыка** — подтверждено, функции нет нигде. Но точнее, чем «нет»: арифметика
   **есть и продублирована** в двух путях показа — `CharactersPage.tsx:1334` и
   `CharacterWizard.tsx:1578` (спасброски там же: `:1322`, `:1558`). Она только показывает: кубик
   не бросается, УС не сравнивается. Адаптер добавляет бросок и сравнение, а модификатор берёт
   аргументом — чтобы не стать ТРЕТЬИМ владельцем этой формулы.
2. **Бросок по сиду.** `dice::roll_expression` непригоден для движка: `roll_set:88` берёт
   `rand::thread_rng()` на каждый бросок, а `parse:29` приватна. Значит «всё остальное адаптер
   только вызывает» неверно для самого броска: нужен `gm/rng.rs::roll`, который использует
   грамматику выражения из `dice.rs` (владелец грамматики один) и ГСЧ кампании (владелец
   случайности один). Без этого §22 и §44 шаг 11 недостижимы.
3. **Спасбросок.** §3.1 перечисляет спасброски среди закрытого, но закрыты они только внутри боя
   и с двумя заглушками: `combat.rs:778` бросает плоский `1d20` **без бонуса существа** —
   `MonsterSavingThrow` (`combat.rs:122`) показывается в бестиарии (`BestiaryPage.tsx:69`) и не
   читается ни одним расчётом, — а СЛ берётся из `PLAYER_SPELL_SAVE_DC_PLACEHOLDER = 13`
   (`combat.rs:15, 779`), хотя `spellSaveDc` в TS существует. Вне боя спасброска нет вообще.

### Чего адаптер не делает

- **Не считает бой.** Передаёт в `combat.rs` по id из бестиария (§4.3).
- **Не ходит в `rules.json` и `spells.json` из ядра** — §3.1 про независимость от издания в силе:
  ядро зовёт адаптер.
- **Не считает модификатор проверки** — берёт аргументом.
- **Не выдаёт атаку персонажа игрока как настоящую.** `start_combat` ставит персонажу
  `PLAYER_ATTACK_BONUS_PLACEHOLDER = 3` и `1d6` (`combat.rs:530-531`), а скорость — жёсткие
  `speed_feet: 30` мимо `Character.speed_feet` (`combat.rs:526`). Адаптер обязан отказывать, а не
  делать вид, что делегировал.

## 6. Порядок первой пачки

**Предложенный порядок неверен в трёх местах.** Предложено: ядро состояния (L), seed и ГСЧ (M),
Оракул (M), напряжение (S), отладочный режим (S) — 15 весов.

1. **Не хватает Fact Store, и Оракул без него нарушает §6.3.** «Оракул не должен использоваться,
   если ответ уже есть в World State» — жёсткое правило, а не пожелание. Оракул, сданный раньше
   Fact Store, будет перебрасывать уже решённый факт, то есть противоречить игроку, и потом будет
   переписан. §41 ставит Fact Store четвёртым, Оракул седьмым.
2. **Сначала надо закрыть путь записи, иначе каждое новое поле движка затирается фронтом.**
   `save_campaign` принимает от фронта ЦЕЛЫЙ документ (`lib.rs:45`, `CampaignContext.tsx:77`).
   Пока это так, запись с устаревшего снимка сносит `engine` — запись 136 в масштабе документа.
3. **Отладочный режим нельзя ставить последним.** §38 — единственный способ проверить арифметику
   Оракула (базовая вероятность → модификатор → итог → бросок → исход). Придя после Оракула, он
   означал бы, что Оракул приняли на слово. Поле `trace` в `ResultObject` едет в карточке ядра;
   последним остаётся только ЭКРАН.

Плюс замечание о напряжении: §7.1 говорит, что в v0.1 напряжение влияет **только** на шанс
события, а Event Engine в первую пачку не входит. Отдельной карточкой оно ничего наблюдаемого не
даёт — поэтому это поле со владельцем внутри карточки ядра, а не карточка.

## 8. Почему дефект 136 здесь невозможен — и чем это ограничено

Запись 136: `updateCharacter` считал новое состояние от снимка своего рендера, лист пишет в одного
героя двумя путями, и вторая запись до перерисовки затирала первую вместе с наложенным состоянием —
безумие сносило с листа «Ослеплённое».

**Для фактов движка этот класс закрыт тремя свойствами, а не дисциплиной:**

1. **Вызывающий не передаёт состояние.** Команда получает намерение. Устаревшего снимка у фронта
   нет, потому что снимка нет вовсе.
2. **Новое состояние считается от диска под замком.** `with_active_locked` (`storage.rs:274`)
   читает, мутирует и пишет под одним удержанием `STORAGE_LOCK`, без окна между чтением и
   записью. Две команды движка не переплетаются — замок их выстраивает в очередь.
3. **Поля `EngineState` приватны, и единственный путь записи — `mutate::apply`.** Это проверяет
   компилятор. В TS то же правило проверялось бы только ревью: идиома `{...current, facts: [...]}`
   доступна любому файлу.

**Чего это не закрывает, честно:**

- **Пока `save_campaign` принимает целый документ, архитектура 136 не закрывает, а переносит.**
  Фронт, сохранивший свой снимок после того, как движок записал свой, снесёт `engine`. Сегодня это
  латентно: из Rust-владений в документе есть только `combat`, и оба пути освежаются через `commit`
  (`CampaignContext.tsx:204`) — гонка требует двух записей в полёте. С движком, который пишет на
  каждое действие, это станет главным режимом отказа. **Поэтому карточка 1 первой пачки — сужение
  `save_campaign`, а не начало движка.**
- **Внутри одной команды** модуль, записавший `EngineState` напрямую вместо выдачи `Mutation`,
  открывает класс заново. Против этого — приватность полей (пункт 3), и она работает ровно до тех
  пор, пока `EngineState` не получит `pub`-поля «для удобства».
- **Три мутатора фронта по-прежнему считают от снимка рендера**: `addCharacter`,
  `removeCharacter`, `setCampaignName` (`CampaignContext.tsx:114, 121, 195`). Это тот самый
  «общий перевод остальных», оставленный своей карточке в записи 136. Движка он не касается, но
  остаётся открытым долгом, и карточка 1 его не отменяет.

## 9. Расхождения концепта с кодом

Список для Producer'а и владельца. **Концепт я не правлю** — правит Producer с владельцем.

1. **§4.1 CampaignState — в коде нет ни одного поля движка.** `CampaignState` (`model.rs:415`) это
   `id`, `campaignName`, `characters`, `journal`, `combat`. Из десяти полей §4.1 нет ни `seed`, ни
   `current_scene_id`, ни `tension`, ни `actors`, ни `locations`, ни `facts`, ни `plot_threads`,
   ни `event_history`. Отдельно: **`system_id` смысла не имеет** — правило одно (SRD 5.1), и поле
   без второго ruleset'а будет постоянным. Предлагаю не заводить, пока второго издания нет.
2. **§4.1 против §4.2 — `tension` объявлено дважды**, у кампании и у сцены. Это дубль в самом
   концепте. Решено: у сцены; при переходе новая сцена берёт значение у закрытой (§7.2).
3. **§4.3 против §4.5 — осведомлённость объявлена дважды:** `Actor.states: ["unaware"]` (пример
   §4.3) и `Threat.awareness` (§4.5, §25). Решено: у угрозы — её читает Context Filter (§8.4).
   `Actor.states` остаётся под состояния вида `hidden`.
4. **§22 — ни сида, ни состояния ГСЧ нет нигде.** `dice.rs::roll_set:88` берёт
   `rand::thread_rng()` на каждый бросок. Сегодня в приложении не воспроизводимо ничего.
   Отдельно: `StdRng::seed_from_u64` в `rand 0.8` уже доступен, новой зависимости не нужно, но
   состояние `StdRng` не сериализуется — поэтому `rng_state` это один `u64`, от которого поток
   пересеивается на каждом обращении. Альтернатива «хранить счётчик и проигрывать заново» стоит
   O(n) на каждый бросок и растёт без предела.
5. **§36 — версий схемы в сохранении нет**, и они не нужны: миграции у нас держатся формой полей
   (`#[serde(default)]`, `#[serde(alias = "knownSpells")]`, `migrate_legacy_gold`,
   `migrate_legacy_spell_slots`, `migrate_legacy_adventure_log`) и работают. Номер версии стал бы
   вторым владельцем ответа «какой это формат». Предлагаю снять §36 или записать как «версия
   живёт в форме полей».
6. **§33 Result Object — в коде нет ничего похожего:** каждая команда возвращает целый
   `CampaignState` (`lib.rs`). Отдельно: `state_changes` со строковыми путями
   (`"actors.pc_vizzerin.states"`) приземляю типизированным `Mutation`, а не строкой — строковый
   путь непроверяем и тянет за собой парсер путей.
7. **§34–§35 — очереди мутаций, валидатора, транзакций и Undo нет.** Состояние пишется целым
   документом: `save_campaign(state)` с фронта (`CampaignContext.tsx:77`) и `save_campaign_in`
   в Rust (`storage.rs:181`).
8. **§18 Template Renderer и локализация — ни того, ни другого.** Текст — русские литералы в
   компонентах; `WORST_LOCALE` и `LOGICAL_BOX` в `.studio/project.conf` стоят TBD. Приземляю как
   «движок владеет ключом, UI владеет строкой»; шаблонизатора `{actor}` в v0.1 нет.
9. **§19 Content Packs — дерева `/content` нет, и заводить его нельзя.** Содержание разрезано по
   происхождению: SRD в `src-tauri/rules/*.json`, переданное владельцем в TS
   (`src/ui/eventTables/`, `wildMagicSurges.ts`, `optionalRules.ts`, `abyssElfRace.ts`,
   `madness.ts`). Довод записан в шапках `eventTables/types.ts` и `optionalRules.ts`: подмешивание
   в `rules.json` сделало бы границу «это SRD» непроверяемой и соврало бы игроку о источнике в
   подвале вкладки «Правила». Единое дерево §19 эту границу ломает.
10. **§29.2 — «всё, что достойно памяти… пишется в дневник кампании» читается как автоматическая
    запись.** Правило набора страницы дневника принадлежит данным и живёт в TS
    (`journalEntryText.ts`, `JOURNAL_ENTRY_MAX_LENGTH`, дописывание в самую свежую страницу).
    Приземлено как «движок предлагает, пишет игрок», по образцу уже работающего генератора
    событий. Нужно подтверждение владельца, что автоматической записи он не имел в виду.
11. **§17 — урон из боя не возвращается никуда.** `Combatant` копирует `max_hp`, `current_hp`,
    `armor_class` персонажа (`combat.rs:517-531`), а `end_combat` выбрасывает `CombatState`
    целиком (`lib.rs:169`): полученный в бою урон не доходит до листа, а урон монстра не
    переживает боя. Поэтому у `Actor` движка **нет и не должно быть HP** — иначе третий владелец.
    Вернёт ли бой результат на лист — решение владельца, не моё.
12. **§3.1 «бой закрыт» верно лишь для монстров.** Персонажу игрока ставятся заглушки:
    `PLAYER_ATTACK_BONUS_PLACEHOLDER = 3`, урон `1d6` (`combat.rs:9-10, 530-531`),
    `PLAYER_SPELL_ATTACK_BONUS_PLACEHOLDER = 5`, `PLAYER_SPELL_SAVE_DC_PLACEHOLDER = 13`
    (`combat.rs:14-15`) — при том что `spellSaveDc` в TS уже есть; скорость персонажа жёстко
    `30` мимо `Character.speed_feet` (`combat.rs:526`). И спасбросок существа бросается плоским
    `1d20` без его бонуса: `MonsterSavingThrow` (`combat.rs:122`) показывается в бестиарии
    (`BestiaryPage.tsx:69`) и не читается ни одним расчётом.
13. **§12.1 — восемь полей NPC против «Basic NPC state» в §41.** Полный список (`role`, `goal`,
    `fear`, `knowledge`, `resources`, `current_intent`) — это §42 v0.2. В v0.1 у актора только
    `attitude` и `states`.
14. **§41 пункт 10 против существующих 26 таблиц к100** в `src/ui/eventTables/`. Это разные вещи:
    там описательная строка для стола, здесь шаблон с машинным `effects`. Сливать нельзя — будет
    два владельца одной таблицы. Отдельно висит уже названный в `eventTables/types.ts` вопрос
    владельцу: две таблицы дикой магии (`d100_всплесков_дикой_магии.pdf` против нашей на 50
    строк) — тоже два владельца одного факта, решение за владельцем.
15. **§39 Телеметрия — нет, и в §41 её нет.** В v0.1 не делать.
16. **`SHOTS_CMD` и `HEADLESS_GAMES_CMD` в `.studio/project.conf` пусты.** §40 «Long Simulation»
    (10 000–100 000 сцен) требует headless-прогона с фиксированным сидом, и он станет возможен
    ровно после карточки 3 первой пачки. Это не расхождение, а зависимость: §40 нельзя обещать
    раньше, чем появится ГСЧ кампании.

Ни один из шестнадцати пунктов не переписан в концепте этим ADR: где я принял решение, оно названо
здесь и помечено словом «решено» или «приземляю».
